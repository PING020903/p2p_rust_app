# NAT 穿透（打洞）方案规划

> 目标：让 `p2p_rust_app` 在两个不同局域网（不同 NAT 之后）的节点之间也能建立连接，
> 最终支持公网 P2P 通讯。本文档先讲清原理（NAT / NAT 类型 / IPv6），再给分阶段实施方案。
>
> 现状（0.16.0）：仅 **TCP + Noise + Yamux** 传输、**mDNS 局域网发现**，无任何公网穿透能力。

---

## 一、背景：NAT 是什么，为什么要打洞

### 1.1 地址与端口

互联网上两台电脑通信，需要**两端地址** `IP:端口`：

- IP：谁（公网全局唯一）
- 端口：这台机器上的哪个程序（0~65535）

家用路由器分给你电脑的是**私网 IP**（如 `192.168.31.10`），它在公网上**没有意义、路由不到**。公网只认**公网 IP**（路由器 WAN 口那个）。

IPv4 地址只有约 43 亿个，设备远超这个数 → **NAT 就是"用一个公网 IP 让整屋设备共享"的应急方案**。

### 1.2 NAT 在干嘛（socket 视角）

你 `connect()`/`sendto()` 时，路由器改写源地址并记一张映射表：

```
你发出:  源 192.168.31.10:50000  → 目标 8.8.8.8:53
路由器改: 源 183.6.x.x:12345     → 目标 8.8.8.8:53     （源换成"公网IP:临时端口"）
表里记:   192.168.31.10:50000 ↔ 183.6.x.x:12345        （只对 8.8.8.8:53 方向有效）
回包:     源 8.8.8.8:53 → 目标 183.6.x.x:12345 → 查表 → 转给你电脑
```

外面世界看到的你永远是 `183.6.x.x:12345`。

### 1.3 致命后果：外网无法主动找你

1. 私网 IP 公网路由不到。
2. 路由器**只转发"有映射的回包"**；一个全新的、你没先发过包的入站连接 → 查表无条目 → **丢弃**。

**C 视角类比**：NAT 映射表像内核 connection 表——只有你 `connect()`/发过包才有条目；别人 `connect()` 进来，SYN 直接丢。

### 1.4 为什么现在局域网能用 mDNS/直连

所有节点在**同一个 NAT 内部**，用私网 IP 直接互通；mDNS 是局域网广播发现。出了你家网络，`/ip4/192.168.31.10/tcp/9022` 这个地址**没人能拨**。

### 1.5 打洞原理

两个 NAT 后的节点谁都无法主动敲对方门 → 打洞：

> **双方同时**向"对方的公网 IP:端口"发包，两个路由器**同时**建立映射 → 中间对上 → 之后直连。

- **中继（relay）**：不赌能不能对上，公网服务器直接转发流量——100% 能通，但慢。
- **打洞（hole punching）**：先经中继认识彼此公网地址，然后同时打洞试直连，成功就甩开中继。

## 二、NAT 的类型

### 2.1 两个维度

| 行为 | 含义 | C 类比 |
|---|---|---|
| **映射行为**（mapping） | 对外发包时分配的"临时公网端口"**对不同目标是否一致** | 门卫给的"临时访客牌号" |
| **过滤行为**（filtering） | 外部能否回包，取决于你是否**先给这个目标发过包** | 门卫递不递门外来信 |

现代标准（RFC 4787）按两个维度独立分类，组合出 4 种经典类型（RFC 3489 STUN 术语）：

| 经典类型 | 映射行为 | 过滤行为 | 能否打洞 |
|---|---|---|---|
| **全锥形** Full Cone | 端点无关 | 不过滤 | ✅ 最容易 |
| **受限锥形** Restricted Cone | 端点无关 | 按目标 IP 过滤 | ✅ 需先向对方发包 |
| **端口受限锥形** Port Restricted Cone | 端点无关 | 按目标 IP+端口 过滤 | ✅ 需先向对方发包 |
| **对称** Symmetric | 端点相关（每目标不同端口） | 通常严格过滤 | ❌ |

### 2.2 关键结论

> **打洞只看"映射行为"：端点无关（发给谁都同一外部端口）就有戏；对称 NAT 打洞必败。**

- 锥形 NAT 的外部端口固定，对方打得到（受限型要求先发过包——**DCUtR 双方同时发包**正好满足）。
- 对称 NAT 向不同目标用不同端口，上报的端口下次就变 → 打不穿 → **只能走中继**。

### 2.3 探测（STUN）

- STUN 服务器回话告诉你"你在我眼里是 `公网IP:端口`"。
- 向**两个不同 STUN 服务器**发请求对比外部端口：一致 → 端点无关（可打洞）；不同 → 对称（不能打洞）。
- 过滤行为需第二台机器测试，对我们不重要（DCUtR 的"同时发包"天然满足受限/端口受限过滤）。

对方案的影响：VPS 上顺手跑一个 STUN 服务（或用公共 STUN），启动时探测 NAT 类型，提示用户"可打洞 / 只能走中继"。

## 三、NAT 与 IPv6

### 3.1 核心认知

**NAT 是 IPv4 的"补丁"，不是 IPv6 的东西。**

- IPv4：地址 43 亿不够用 → NAT 让整屋共享一个公网 IP。
- IPv6：128 位地址（≈3.4×10³⁸），设计初衷是**每设备一个全球唯一公网地址**，**不需要 NAT**。

所以**没有"IPv6 版本的 NAT"**（没有私网不可达→翻译这回事）。

### 3.2 但 IPv6 现实也没那么干净

| 现象 | 是什么 | 是否影响打洞 |
|---|---|---|
| **NAT66 / NPTv6** | ISP 改写你的 IPv6 前缀（一对一翻译） | 基本不影响 |
| **NAT64** | IPv6 ↔ IPv4 协议翻译（网关转换） | 无关 |
| **家用路由器默认防火墙** | 很多路由器即使有公网 IPv6，**默认丢弃入站** | ⚠️ 这才是 IPv6 的主要障碍 |

### 3.3 一句话

> **IPv6 无 NAT，但可能被防火墙挡（要放行，不用打洞）；IPv4 有 NAT，需要打洞，对称 NAT 打不了只能中继。**

### 3.4 对方案的影响：双栈策略

```
双方都有公网 IPv6 且路由器放行  → IPv6 直连（零成本，最优）
        ↓ 不行（防火墙挡 / 无 IPv6）
IPv4 锥形 NAT                   → DCUtR 打洞直连
        ↓ 不行（对称 NAT / 打洞失败）
Relay 中继兜底（100% 能通）
```

工程上：libp2p 的 multiaddr 已原生支持 `/ip6/...`（当前监听里已有 `/ip6/::1/tcp/...`），PeerId 与地址族无关。只需在发现/拨号时纳入 IPv6 地址，优先直连。国内家庭宽带基本有 IPv6 下发，但路由器默认挡入站很常见——不能当唯一路径。

### 3.5 澄清："NAT"本身没有版本号

NAT 是一种**行为**，不是带版本号的协议。带版本的是配套**标准协议**：

- **STUN**：RFC 3489（旧）→ 5389（打洞的地址探测）
- **TURN / ICE**：TURN 是中继协议，ICE 是"打洞 + 中继综合决策"框架（RFC 5245 → 8445）
- **UPnP IGD / NAT-PMP / PCP**：内网设备主动向路由器申请端口映射的协议

## 四、目标架构（libp2p 0.56 标准 NAT 栈）

```
公网服务器 (VPS)
├── Relay (circuit v2)    ← 中继：转发 Noise 加密流量（看不到明文）
└── 房间服务 (rendezvous)  ← 交换节点地址（房间码 → 地址簿）
    └── (可选) STUN       ← NAT 类型探测

客户端 A（NAT后）──①经 relay 建连──→ 客户端 B（NAT后）
        └─②DCUtR 同时向对方公网地址发包 → 打洞成功 → ③升级直连，relay 退位
```

四个关键组件（libp2p 已内置协议）：

1. **Relay (circuit v2)** — 中继，任何 NAT 都能通的兜底路径。
2. **DCUtR (Direct Connection Upgrade through Relay)** — 打洞核心：经 relay 交换连接信息后，双方**同时**向对方公网地址发包，成功即升级直连。
3. **Rendezvous / 房间** — 公网发现层（替代 mDNS 在公网的作用）。
4. **UPnP + QUIC** — 家用路由端口映射 + UDP 传输（UDP 打洞成功率远高于 TCP）。

**安全**：relay 只做字节搬运，转发的是 **Noise 端到端加密**流量，**中继服务器无法解密**。身份/TOFU/加密栈跨公网直接复用，PeerId 稳定不变。

## 五、对现有工程的影响

| 模块 | 改动 |
|---|---|
| **L1 传输层 `node.rs`**（最大改动） | transport 加 QUIC(UDP) + 用 `nat::ExtTransport` 包装；`NodeBehaviour` 加 `relay client`、`dcutr`、`upnp`、`identify`、`nat`；支持拨号 relay 地址 `/p2p/<relay>/p2p-circuit/p2p/<peerid>` |
| **L1 发现层** | mDNS 保留（局域网）；新增房间/会合机制（公网） |
| **L2/L3（身份/会话/群）** | **几乎不变**——连接一旦建立，心跳/消息/群聊全部照旧 |
| **配置/命令** | 新增：设置 relay 服务器地址、`/room <码>` 加入房间等 |

Cargo.toml 需加 features：`relay`、`dcutr`、`upnp`、`nat`、`quic`、`identify`（0.56 具体 API 实现时核对）。

## 六、分阶段实施方案

### 阶段 1 — 中继连通（最小可用）

- VPS 上跑 relay 服务器（复用本工程，加 relay 模式/单独二进制）。
- 客户端加 relay client + identify；支持 `/dial` relay 地址。
- 目标：两个 NAT 后节点**经 relay** 收发消息/群聊。
- 这步不涉及打洞，先把"公网能连通"打通。

### 阶段 2 — 房间/发现

- 服务器加简单房间服务（房间码 → 地址簿交换）。
- 客户端 `/room <码>` 加入 → 自动发现同房间节点 → 经 relay 拨号。
- 目标：输入房间码即互通，不再手贴地址。

### 阶段 3 — DCUtR 直连打洞（核心）

- 加 `dcutr` behaviour；客户端自动尝试直连打洞，成功则升级、relay 退位。
- 加 QUIC(UDP) transport 提升打洞成功率。
- 目标：锥形 NAT 节点直连（低延迟），对称 NAT 自动回落 relay。

### 阶段 4 — 优化

- UPnP 端口映射（家用路由），节点获得公网可达地址。
- NAT 类型探测 + 界面提示（"当前打洞可行性"）。
- 中继带宽/时延观察、心跳调优。

## 七、基础设施需求

- **1 台公网 VPS**（低配即可，relay 只转发小流量）——**硬前提**，打洞必须有个公网传信点。
- 位置建议：国内（延迟低，可能需备案/实名）或香港（免备案，延迟尚可）。
- 服务器跑：relay Server + 房间服务（+ 可选 STUN），资源占用很低。

## 八、风险与取舍

1. **对称 NAT 打洞必然失败**（移动网/运营商 NAT444 常见）→ 只能长期走 relay（延迟/带宽受服务器限制）。
2. **国内网络**：运营商大 NAT、UDP 可能被 QoS/封 → QUIC 成功率不确定。
3. **服务器单点**：relay 挂了，公网互通就断（多 relay 缓解，先不做）。
4. **libp2p 0.56 nat 模块 API 有版本变动**，实现时需按文档核对。
5. 发现层从"局域网 mDNS 自动发现"变成"公网房间码手动加入"——**体验降级**（公网无自动发现，除非上 DHT，暂不建议）。
6. IPv6 是"免打洞"捷径但常被家用路由器默认防火墙挡住。

1. **有没有可用的公网服务器（VPS/云主机）？** 有的话什么网络（国内/香港/国外）？这是整个方案的硬前提。
2. **目标场景**：双方都在家里宽带？办公室/校园网（防火墙更严）？要不要考虑手机移动网（对称 NAT 多）？
3. **接受先自建 relay+房间服务器**，还是先做一个"手动互贴 relay 地址"的最简版试试水？

5. 传输层要不要上 **QUIC/UDP**（打洞成功率关键），还是先只用 TCP？
